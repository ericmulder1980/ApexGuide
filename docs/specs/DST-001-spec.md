# DST-001: Pilot builds (signed APK and TestFlight)

## Overview

Produce the first distributable builds of ApexGuide: a signed Android APK that pilot testers install from a link, and an iPhone build uploaded to TestFlight. The 2016 MacBook Pro cannot run Xcode 26, so iOS builds run on a GitHub Actions macOS runner (DEC-006); this is the app's first iOS build (DEC-011). DST-001 also changes the app ID to `nl.webmiller.apexguide` before anything is registered with a store, opens the developer accounts, and creates the signing keys. Decisions: DEC-014 (app ID), DEC-015 (distribution accounts and CI security).

## User Stories

**Primary:** As the owner, I want signed pilot builds for Android and iPhone from a repeatable pipeline, so pilot testers can install ApexGuide and I can ship updates without a Mac that runs Xcode 26.

**Additional:**
- As a pilot tester on Android, I want to install the app from a link, so I don't need a store account.
- As a pilot tester on iPhone, I want to install the app through TestFlight.

## Acceptance Criteria

- [ ] App ID `nl.webmiller.apexguide` on Android (applicationId, namespace) and iOS (bundle ID), before any store registration (DEC-014)
- [ ] Apple Developer Program (individual enrollment) and Google Play Console accounts opened; Android developer verification started
- [ ] Android app signing key created outside the repo, backed up offline, and usable later as the Play app signing key through PEPK
- [ ] Signed, obfuscated release APK built by a GitHub Actions workflow and published as a GitHub pre-release, installable from its download link
- [ ] iOS release build compiles on a GitHub Actions macOS runner with Xcode 26 (App Store requirement since 28 April 2026)
- [ ] macOS workflow signs the IPA and uploads it to TestFlight; the owner installs it through internal testing
- [ ] Signing secrets live only in a protected GitHub environment, never in the repo or workflow logs
- [ ] Workflows are safe in a public repository: manual trigger only, no `pull_request_target`, read-only token permissions, third-party actions pinned to a commit SHA
- [ ] `ITSAppUsesNonExemptEncryption` set according to the export-compliance outcome for SQLite3 Multiple Ciphers
- [ ] Debug symbols from `--split-debug-info` kept as workflow artifacts, never committed
- [ ] Builds use the ApexGuide launcher icon from FND-001

## Scope

**Out of scope:**
- TestFlight external group and invite link: needs Apple's beta review, which a placeholder app is likely to fail (guideline 2.1); starts when the app has pilot content, with a demo key for the reviewer (DEC-009, DST-002)
- Play Console testing tracks and store listings (DST-002)
- Tests on every push and automatic uploads on tags (OPS-001)
- The production API URL (ISS-008); builds take the config file as a workflow input

## Technical Design

### App ID

`nl.webmiller.apexguide` replaces `com.apexguide.app` on both platforms: Android `applicationId` and `namespace` (with `MainActivity` moving to `kotlin/nl/webmiller/apexguide/`), iOS `PRODUCT_BUNDLE_IDENTIFIER` for Runner and RunnerTests. The display name stays "ApexGuide". The change must land before the App ID is registered with Apple or the first APK reaches a tester, because both make the ID effectively permanent.

### Accounts

| Account | Type | Owner actions |
| --- | --- | --- |
| Apple Developer Program | Individual (WebMiller is an eenmanszaak; Apple accepts only legal entities as organisations). The owner's legal name is the seller; Apple Developer Support can convert to an organisation if WebMiller becomes a BV | Apple Account with two-factor authentication, enrollment fee, identity verification |
| Google Play Console | Organisation if WebMiller has a D-U-N-S number, otherwise personal. Personal accounts must run a closed test before production access | D-U-N-S lookup, registration fee, identity and organisation verification |
| Android developer verification | Required for sideloaded apps on certified devices: first countries from September 2026, global from 2027 | Register the package name and signing certificate |

### Android signing

One app signing key (RSA 4096, validity beyond 2050) generated by the owner with `keytool`, so the passwords never pass through tools or logs. It is stored in a password manager plus an offline backup. Locally it is referenced from `android/key.properties` (git-ignored, FND-001 review). In CI the keystore is a base64 GitHub secret, written to the runner's temp directory and deleted at the end of the job. When the Play Console account exists, the same key is uploaded as the Play app signing key with PEPK, so pilot installs can update from Play.

### Workflows

| Workflow | Runner | Trigger | Output |
| --- | --- | --- | --- |
| `android-release.yml` | `ubuntu-latest` | `workflow_dispatch` (config file input, default `config/prod.json`) | Signed release APK attached to a GitHub pre-release; debug symbols as a workflow artifact; `apksigner verify` output in the log |
| `ios-build-check.yml` | `macos-26`, Xcode pinned to 26.3 | `workflow_dispatch` | Unsigned `flutter build ios --release --no-codesign`; proves the toolchain without an Apple account |
| `ios-testflight.yml` | `macos-26`, same Xcode | `workflow_dispatch` | Signed IPA uploaded to TestFlight with `xcrun altool --upload-app` and an App Store Connect API key; debug symbols as artifact |

Shared rules for all workflows:
- Flutter 3.38.10 (DEC-012) through a pinned setup action, with `flutter analyze` and `flutter test` before building
- `permissions: contents: read` by default; only the job that creates the GitHub release gets `contents: write`; no `pull_request` or `pull_request_target` triggers
- Signing secrets in a GitHub environment `release` with the owner as required reviewer, so every signed build needs the owner's approval
- Third-party actions pinned to a full commit SHA
- Build number from `github.run_number`; version name from `pubspec.yaml`
- `--obfuscate --split-debug-info=build/symbols`; symbols uploaded as an artifact with limited retention

Xcode 26.3 is pinned first because it is closest to Flutter 3.38.10's release; newer Xcode 26 versions have reported Flutter build problems. If 26.3 fails, the build check tries the other Xcode 26 versions on the image before anything else changes.

### iOS signing

Manual signing in CI: an Apple Distribution certificate (`.p12`) and an App Store provisioning profile for `nl.webmiller.apexguide`, both as base64 secrets, imported into a temporary keychain on the runner and removed afterwards. The App Store Connect API key (`.p8`, App Manager role) authenticates the upload. `ExportOptions.plist` is generated in the workflow from secrets and never committed (it is git-ignored).

### Export compliance

SQLite3 Multiple Ciphers encrypts the local database (FND-004). Whether that qualifies for an exemption under Apple's export-compliance questions decides `ITSAppUsesNonExemptEncryption` in `Info.plist`. This is researched in T6 and recorded in DEC-015.

### APK link

The workflow publishes the signed APK as a GitHub pre-release tagged `pilot-v<version>+<build>`. Testers install it from the release's download link. The APK is public, which is acceptable: the app does nothing without a license key (DEC-004). Debug symbols stay a workflow artifact and are never attached to the release.

### Key decisions

| Decision | Recommendation | Recorded in |
| --- | --- | --- |
| App ID | `nl.webmiller.apexguide` | DEC-014 |
| Apple account | Individual enrollment; convert if WebMiller becomes a BV | DEC-015 |
| Repository visibility | Public (free macOS runner minutes); LICENSE no longer says "confidential" | DEC-013 update |
| Upload tooling | `xcrun altool` with an App Store Connect API key; fastlane deferred to OPS-001 | DEC-015 |

### Risks

| Risk | Likelihood | Impact | Mitigation |
| --- | --- | --- | --- |
| Flutter 3.38.10 fails with the runner's Xcode 26 | Medium | High | Build check first (T5); pin Xcode 26.3; try other Xcode 26 versions; last resort is a newer Flutter in CI only, which needs a new decision |
| Account verification takes weeks | Medium | High | Start accounts first (T2); T1, T3, T4 and T5 do not need them |
| Signing key lost | Low | High | Password manager plus offline backup; Play app signing after PEPK upload |
| Secrets leak from a public repository | Low | High | Manual triggers only, protected environment with required reviewer, read-only token, pinned actions, no secrets in logs |
| Sideloaded APK blocked by Android developer verification | Low in pilot | Medium | Verification started in T2; Netherlands enforcement expected from 2027 |
| Placeholder app rejected by TestFlight beta review | High if tried | Low | Internal testing only in DST-001 |
